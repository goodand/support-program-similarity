# 신규사업 검토 순위 비교 (2026-11-12)

공고 668개 풀에서 공고 하나를 질의로 넣었을 때, 사람이 비슷하다고 묶은 공고(평가셋 사업 35개·그룹 14개)를 몇 위 안에서 모두 찾는지 방법별로 비교했다.

## 지표

질의마다 같은 그룹 공고를 모두 찾을 때까지 읽는 후보 수(마지막 정답 순위)를 구하고, 질의 35개 중 가장 나쁜 값을 기준으로 쓴다. 이 값까지 검토하면 모든 질의에서 정답을 100% 찾는다. 질의 자신은 후보에서 뺀다(후보 667개).

## 결과 (가장 나쁜 마지막 정답 순위)

| 방법 | 공고명만 | 청크(9칸) |
|---|---|---|
| 키워드 (BM25) | 미측정 | 16 |
| 임베딩 학습 전 (단독 / 결합) | 130 / 미측정 | 12 / 9 |
| 임베딩 학습 후 (단독 / 결합) | 104 / 미측정 | **8 / 8** |
| Decision Model flash | 75 (별도 세션 보고, 미재확인) | 27.5 (별도 세션 보고, 미재확인) |
| Haiku 5.5 low | 18 | 30위 밖 5개 |
| Sonnet 5.5 low | 18 | 15 |
| Sonnet 5.5 high | 19 | 15 |
| Opus 5.5 low | 19 | 11 |
| Opus 5.5 high | 16 | 11 |

- 청크 9칸: 26공고명, 기관, 대분류, 중분류, 업종, 목적, 내용, 대상, 대상유형을 "칸 이름: 값"으로 ` / ` 연결.
- 9칸 + 지원규모(학습 후 단독): 가장 나쁜 순위 8, 평균 3.34(9칸은 3.09). 개선 없음.
- 결합 = 키워드와 임베딩 유사도를 질의별 최소·최대로 0~1에 맞춘 뒤 반씩 더한 점수.

## LLM 조건 실행 방식

- 질의마다 `claude -p`를 새로 띄워 따로 호출(35회). 프로젝트 지침·메모리·도구·MCP·세션 저장을 끄고 빈 고정 폴더에서 실행.
- 입력: 후보 668개 전체 목록(고정 순서) + 지시문 + 질의 1개. 상위 30개 후보 번호를 JSON으로 받음.
- 응답 처리 규칙: 질의 자신의 번호는 채점에서 제외. 'A if False else B'는 B로 읽음(1건 해당).
- 재실행: 사용량 한도 오류 16건, 결과 칸이 빈 응답 1건만 다시 실행. 원래 파일은 따로 보관.

## 한계

- 각 조건 1회 실행. 후보를 번호 순서대로 넣어, 번호가 붙은 비슷한 공고 묶음을 통째로 내놓는 경향이 보였다. 순서를 섞은 재실행은 미실행.
- 형제 공고(같은 세부사업에서 괄호만 다른 공고)가 정답 짝보다 앞에 오는 경우(G22)는 사람 평가 결과와 대조 예정.
- 비용은 CLI 보고값이 공식 단가와 맞지 않아(Haiku 약 70~80배) 토큰 수 x 공식 단가로 다시 계산한다.

## 파일

- `scripts/`: 실행·채점·검증 스크립트. 경로는 환경변수(`WORKFLOW_RUNNER_DIR`, `ISO_CWD`, `NOTICE_MASTER_XLSX`, `NOTICE_MASTER_SHEET_PREFIX`)로 받는다.
- `VERIFY_LOG.md`: 질의별 결과 파일에서 순위를 다시 계산해 요약과 대조한 기록.
- 입력 데이터(공고 텍스트·임베딩)는 공개하지 않는다.
