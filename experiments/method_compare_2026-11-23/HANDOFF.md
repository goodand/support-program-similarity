# 인계: 방법별 검색 성능 비교와 파인튜닝 (2026-11-23 기준)

다른 PC에서 이 문서 하나로 전체 맥락을 이어받기 위한 안내입니다. 앞부분은 목적과 확정된 결과, 뒷부분은 파일·경로·실행 명령입니다.

## 1. 목적과 판단 기준

- **궁극 목적:** 지원사업 공고를 사람이 검토할 때 드는 비용을 낮춥니다. 신규 공고 하나를 질의로 넣으면, 비슷한 기존 공고가 목록 앞쪽에 모이게 합니다.
- **성공의 뜻:** 검토자가 목록을 위에서부터 읽을 때, 정답(비슷한 사업)을 모두 만나는 지점이 앞쪽에 있습니다. 그래서 대표 지표는 "마지막 정답 순위"입니다.
- **판단 주체:** 방법 채택, 보고서 표기, 병합은 사용자가 정합니다. 에이전트는 측정하고 근거를 제시합니다.
- **신뢰 기준:** 숫자는 결과 파일에서 직접 계산한 값만 씁니다. 문서 간 숫자를 비교할 때는 값마다 연도와 출처를 붙입니다.
- **평가셋의 뜻:** 정답은 "유사 사업" 판정입니다(같은 사업 판정과 다른 개념). 평가셋은 "그룹 14개·질의 35개"로 부릅니다.

## 2. 평가 구성

| 항목 | 값 |
|---|---|
| 후보 풀 | 2026년 공고 668개 (질의 자신을 뺀 후보 667개) |
| 평가셋 | 그룹 14개, 질의 35개, 쌍 30개 (경영 분야) |
| 그룹 크기 | G08 2, G09 2, G10 4, G13 2, G14 3, G15 2, G20 2, G22 2, G23 2, G24 2, G25 3, G26 3, G27 4, G28 2 |
| 입력 조건 2개 | 청크 9칸 / 공고명만 |
| 순위 규칙 | 점수 방법은 `eval_v3.py`의 `rank()`(동점은 가운데 순위), LLM은 응답 목록 위치 |

**청크 9칸**은 공고 한 건의 9개 항목을 " / "로 이은 한 줄입니다: 26공고명, 기관, 대분류, 중분류, 업종, 목적, 내용, 대상, 대상유형. 668개 중 665개는 9칸이 모두 채워져 있고 3개는 일부 칸이 비어 있습니다.

**지표**
- 마지막 정답 순위: 질의마다 정답 중 가장 뒤에 있는 정답의 순위. 질의 35개에 대해 최악·평균·중앙값을 냅니다.
- Recall@8 (macro): 질의마다 정답 중 8위 안에 든 비율을 구해 35개 평균.
- MAP: 질의마다 정답 순위를 오름차순으로 놓고 k번째 정답의 k/순위를 평균한 뒤 35개 평균.

## 4. 방법별 설명

### 4-1. 키워드(BM25)
- Kiwi 형태소 분석기(kiwipiepy 0.24.0, 분석기 설정 `kiwi_space1_jabudam0_malware0`, 문장부호 토큰 제외)로 토큰을 만듭니다.
- 점수는 BM25(bv=1.0, bs=0.75, k1=1.5)이고, 질의→후보와 후보→질의 두 방향의 평균입니다.
- 공고명 입력도 같은 분석기 함수로 공고명 668개를 토큰화했습니다. 예: "2026년 고령자 계속고용장려금" → `2026 / 년 / 고령자 / 계속 / 고용 / 장려금`.

### 4-2. 하이브리드(임베딩 + 키워드)
- 질의 행마다 키워드 점수와 임베딩 점수를 각각 그 행의 최솟값·최댓값으로 0~1로 맞춘 뒤 0.5씩 더합니다.
- 그 값과 방향을 바꾼 값을 평균합니다((W + Wᵀ)/2).

### 4-3. 임베딩과 파인튜닝
- 기반 모델은 Qwen3-Embedding-8B입니다. 학습 조건 전체는 `experiments/embedding_ft/CONDITIONS.md`에 있습니다.
- 요약: LoRA(r 16, alpha 32), batch 128, 5스텝(640짝), 학습률 2e-4, Contriever식 자르기(crop)로 만든 짝, MultipleNegativesRankingLoss.
- LoRA 어댑터는 따로 저장하고, 쓸 때 `peft.PeftModel.from_pretrained`로 기반 모델에 붙입니다(기반 모델 가중치는 그대로 유지).
- **학습 batch의 뜻:** batch 하나가 순전파·역전파·갱신 한 번(1스텝)입니다. batch 128이면 문장마다 묶음 안 오답이 127개입니다.
- **batch 128의 근거:** 코드 기본값은 64이고, 128은 "묶음이 클수록 묶음 안 오답이 많다"는 가설로 시도했습니다. 96GB GPU에서 최대 70.1GB를 썼습니다. 같은 조건(학습률 2e-4, 1 epoch, seed 42)의 64 대 128 비교는 판단불가: 구간 0 포함이었습니다.
- **기준 실행을 고른 경위:** 5스텝 실행은 원래 메모리 사용량 시험이었고, 평가셋 점수를 본 뒤에 기준으로 골랐습니다. 보고서에는 이 사실을 함께 적습니다.
- **학습량 단위:** 5스텝 × 128 = 640짝, 1 epoch = 9,321짝(72스텝), 2 epoch = 144스텝.

### 4-4. 인코딩 설정과 점수 계산
- 인코딩은 bf16, 최대 2048 토큰, 프롬프트 생략(질의와 문서를 같은 방식으로), L2 정규화 후 float32 저장입니다. 668개 평가용 인코딩의 batch size는 16입니다.
- **표의 임베딩 점수는 저장된 벡터의 내적입니다.** 저장 벡터의 길이가 0.9965~1.0039(bf16 반올림)라서 내적과 코사인 유사도가 미세하게 다릅니다.
- **인코딩 batch size의 영향:** 작동 원리는 같습니다. GPU 효율을 위해 여러 문장을 묶어 동시에 계산하면 덧셈 순서가 달라지고, 그에 따른 반올림 차이로 벡터 값에 미세한 오차가 생깁니다.

### 4-5. 재현 실험(별도 폴더에서 처음부터 다시 실행, 11-19)

|---|---|---|---|

| batch 4, 코사인 (재현 실험의 보고값) | 8 | 3.0857 | 0.7323 |

- 재현 실험과 결과 표의 차이는 질의 3개에서 나옵니다(시트 행 번호 523, 44, 58). 정답과 경쟁 후보의 점수 차가 0.0002~0.002로 아주 작은 질의입니다.
- MAP 차이는 주로 점수 계산 방식(내적 대 코사인)에서 나오고, batch size의 영향은 질의 523과 58에 한정됩니다.

### 4-6. Decision Model
- 모델: `pplx-decider-flash-v1.2`(4B)와 `pplx-decider-v1.2`(27B).
- 질의 공고 1개와 후보 667개를 하나씩 짝지어 넣습니다. 입력은 세 부분입니다.
  1. 질문(모든 쌍 공통, 예/아니오형): "공고 A와 공고 B는 지원 목적과 지원 대상이 비슷한 유사 사업인가?" 선택지는 true = "유사한 사업이다", false = "유사한 사업이 아니다".
  2. 공고 쌍: `{"공고 A": <질의 공고 텍스트>, "공고 B": <후보 공고 텍스트>}` JSON 문자열.
  3. 공고 텍스트: 청크 입력은 9칸 문자열 그대로(임베딩 입력과 sha256이 668/668 일치), 공고명 입력은 맨 앞 공고명만.
- 점수는 true 로짓 − false 로짓이고 온도는 1로 둡니다.
- 우리 코드가 덧붙이는 문구는 위 세 가지가 전부입니다. 라이브러리(`pplx_decider`) 내부 템플릿은 확인할 항목으로 남아 있습니다.
- 27B 청크 입력은 행당 약 96초, 668행에 약 18시간이 걸렸습니다(행 단위 캐시로 중단 후 재개).

### 4-7. LLM 순위
- 질의 공고와 후보 667개를 주고 비슷한 순서로 상위 30개(또는 100개)를 답하게 합니다. 비용은 토큰 수 × 정가입니다.
- 상세는 `newreview-compare-2026-11-12` branch의 `experiments/newreview_compare_2026-11-12/` 문서에 있습니다.

## 8. 실행 방법

**GPU 여유와 무관하게 가능한 일**
- 3절 표 다시 계산: 7절 입력을 같은 상대 경로에 두고 아래 순서로 실행합니다. `calc`는 임베딩 환경(numpy, scipy), `xlsx`는 openpyxl이 있는 환경을 씁니다.
  ```
  <EMBED_ENV_PYTHON> -I -X utf8 runs/044/method_compare_xlsx_harness.py calc
  .venv/Scripts/python.exe -X utf8 runs/044/method_compare_xlsx_harness.py xlsx
  ```
  `calc`는 청크 토큰으로 기존 최솟값·최댓값을 다시 만들어 일치를 확인한 뒤 진행합니다(스크립트 안 assert).
- 공고명 Kiwi 토큰: `<KIWI_ENV_PYTHON> -X utf8 runs/044/name_enc_harness/tokenize_name_kiwi_harness.py` (kiwipiepy 0.24.0 환경).
- 보고서 작성, 외부 평가자 판정 대조, 표·문서 정리.

**GPU가 필요한 일(원래 PC: RTX PRO 6000 96GB)**
- 파인튜닝: `experiments/embedding_ft/seed_repeat_b3b128_mem5.sh <seed...>` (Docker 이미지 `embed-ft:20261102-v1`).
- 새 텍스트 인코딩: `code/encode_adapter.py`.
- Decision Model: `DEC_INPUT=full9`(청크) 또는 기본값(공고명), `DEC_CK`로 모델 폴더, `DEC_TAG`로 출력 이름을 정해 `decider_rank.py run` → `eval`. 27B는 약 63GB를 씁니다.
- GPU 작업은 한 번에 하나씩 돌리고, 겹쳐 돌릴 때는 사용자 승인을 먼저 받습니다.

**원래 PC의 환경 메모**
